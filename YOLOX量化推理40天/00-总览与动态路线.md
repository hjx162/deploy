## 北极星与边界

**目标**：以 `模型/yolox_s.onnx` 为唯一模型源，做一个纯 NumPy 的 YOLOX-s 推理框架，再扩展到 NumPy int8 模拟量化，最后用 CUDA 实现 float32 和 int8 推理。

**核心交付物**：

- [ ] NumPy float32：YOLOX-s 全模型输出与 ONNXRuntime 对齐（max abs diff < 1e-3）
- [ ] NumPy 前后处理：letterbox + decode + NMS，检测结果与 ORT 一致
- [ ] NumPy int8：模拟量化全模型，精度可评估
- [ ] CUDA float32：GPU 全模型跑通
- [ ] CUDA int8：dp4a 卷积 + 全模型跑通（加分项）
- [ ] 一份可复现的 benchmark + 总结

**非目标**（这 40 天不做）：

- 训练/微调 YOLOX、QAT 训练
- 完整 COCO SOTA 调参
- 生产级 TensorRT 替代品
- 支持所有 ONNX 算子/动态 shape

## 代码区定位

- **手搓区**：`核心框架/`、`算子演示/`、`验证工具/`、`DAG学习/`。这些是学习者从零写的草稿/半成品，不是第三方工具；P0–P3 先自己写新实现，再对照旧草稿/ORT，旧代码只读参考、不先跑。
- **外部依赖**：NumPy（框架运行时）；ONNX/ONNXRuntime（模型解析 + 参考对拍，不是框架依赖）。
- **模型资产**：`模型/yolox_s.onnx`；`.pth` 不参与推理。
- **AI 边界**：AI 负责 review、定位 bug、给接口/思路/验收标准；核心算子、执行器、量化 kernel 由学习者自己写。

## 关键事实（2026-10-27 从模型读出）

| 项目 | 值 |
|---|---|
| 模型 | `模型/yolox_s.onnx`（opset 11） |
| 输入 | `inputs` (1,3,640,640)，RGB、0–255、letterbox |
| 输出 | `outputs` (1,8400,85)，80×80 → 40×40 → 20×20，原始网格值 |
| 节点 | 279 |
| 算子 | Conv 83、Sigmoid 80、Mul 74、Concat 18、Slice 8、Add 7、MaxPool 3、Reshape 3、Resize 2、Transpose 1 |
| 权重 | 176 initializers（168 fp32 + 8 int64），8.96M 参数 |
| 计算量 | 26.69 GFLOPs |
| ORT CPU | 约 54 ms（M5 Pro，随机输入，5 次平均） |
| 本机 | Apple M5 Pro，无 NVIDIA GPU；CUDA 阶段走 GitHub → N 卡机器 |
| 远程仓库 | `https://github.com/hjx162/deploy.git`（当前为空仓库） |

> [!note] 双机分工
> - **Mac（M5 Pro）**：P0–P3（D1–D15），NumPy float / int8、前后处理、量化。
> - **NVIDIA 机器**：P4–P6（D16–D30），CUDA 基础、GPU float / int8。
> - **P7–P8**：任一机器；CUDA 集成留在 N 卡机器，文档/总结可在 Mac。
> - 切换方式：`git push` → N 卡机器 `git clone/pull` → 复现基线 → 开始 CUDA。详见 [[11-双机Git工作流]]。

**模型结构速记**：

- `83 Conv = 74 个 Conv+SiLU + 9 个 head 预测卷积（3 尺度 × cls/reg/obj）`
- `80 Sigmoid = 74 个 SiLU + 6 个输出层 obj/cls sigmoid`
- 所有 Conv 都是 `group=1`、带 bias；kernel 只有 1×1 / 3×3；stride 只有 1 / 2；pad 只有 0 / 1。
- Focus 在 ONNX 里是 8 个通用 Slice + 1 个 Concat，不是自定义算子；顺序是 TL、BL、TR、BR。
- 输出 85 通道 = 4 reg + 1 obj + 80 cls；obj/cls 已经过 sigmoid，reg 前 4 维是原始值，需要 decode。

## 动态优化协议

> [!important] 核心原则
> 计划是假设，不是合同。可以调整路线，但不能丢掉北极星；可以优化后续阶段，但不要反复重写已经完成的阶段。

### 什么时候复盘

- **阶段结束**：必须复盘，30–60 分钟，填写该阶段文档的「阶段复盘」。
- **每周一次轻量检查**：10 分钟，只看进度、卡点、时间偏差，不改路线。
- **触发式复盘**：同一问题卡住 3 天，或某阶段用时超过计划的 150%，立即停下来复盘，不要硬扛。

### 复盘输入（证据优先）

至少提供：

1. 该阶段文档的「阶段复盘」。
2. 代码路径 + 关键文件。
3. 实际跑过的命令和输出（不要只说“跑通了”）。
4. 性能/精度数字（延迟、误差、mAP、显存）。
5. 3 个具体问题，按优先级排序。

### 复盘输出（AI 侧）

我按这个格式回复：

1. **结论**：这一阶段是否达到硬验收；问题属于知识缺口、bug、估算偏差、环境问题还是动力问题。
2. **证据**：我依据哪些输出下判断。
3. **选项**：2–3 条可选调整，写清代价。
4. **推荐**：选哪条，为什么。
5. **改动**：只改后续阶段文档；已完成的阶段只追加「变更记录/勘误」，不改写历史。
6. **风险**：这次调整可能带来什么新风险。

### 约束

- 每次复盘最多做 **2 个结构性调整**（调整顺序、增删阶段、换技术方案）；小任务增删不限。
- 后续阶段至少保留 **20% 缓冲**。
- 不因为“看起来更高级”而加工具/框架；每个新增项必须回答“它替代了哪个原有任务，或解决了哪个具体卡点”。
- 如果某阶段超时 > 150%，优先 **缩范围**，而不是压缩验收标准。
- 如果连续 3 天没有可展示的进展，先停下来查环境/方法/资料，不要继续堆时间。
- 北极星（NumPy + int8 + CUDA 的 YOLOX 推理）不轻易改；要改必须由你明确决定，并记录原因。

### 失败分类

复盘时先给失败归类，不同类别的修法不同：

| 类型 | 表现 | 修法 |
|---|---|---|
| 知识缺口 | 看不懂公式/API/报错 | 补 1–2 天基础，插入 mini-phase |
| Bug | 输出不对、形状不对、NaN | 逐层对拍，缩小到最小复现 |
| 估算偏差 | 任务量明显超过预期 | 缩范围/拆任务/延期，不降验收 |
| 环境问题 | 驱动、CUDA、依赖、网络 | 先修环境，暂停新内容 |
| 动力问题 | 拖延、焦虑、频繁换方向 | 缩小当天任务，先拿一个小胜利 |

## 学习原则

1. **先正确，再快，再量化，再 CUDA**。顺序不要跳。
2. **ONNX 是唯一模型源**，手写 DAG 只做学习和可视化。
3. **ORT 是推理真值**，推理对拍不需要 torch。
4. **每层可对拍**，不要等全模型跑完才发现第一层就错了。
5. **一次只改一个变量**：布局、量化、并行，分开验证。
6. **性能优化前先有基线**：延迟、FLOPs、每层耗时。
7. **文档记录证据**：命令、输出、数字，不写“感觉学会了”。
8. **手搓区代码自己写**：`核心框架/`、`算子演示/`、`验证工具/`、`DAG学习/` 里的核心实现由学习者完成；先自己写新实现，不先跑旧脚本，旧代码只读参考。AI 只 review、定位 bug、给思路，不代写。
